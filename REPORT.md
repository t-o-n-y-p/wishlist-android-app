## Краткое описание проекта

### Purpose
Kotlin/Android client app for a "Wishlist" REST backend: users register/log in, create and edit wishlists, add gifts, and reserve or delete gifts. All data comes from an HTTP API (Retrofit + OkHttp), authenticated with a Bearer token and a session-id header. No local database — SharedPreferences only.

### Modules (Gradle multi-project)
- **`:app`** — the Android application: UI (fragments), DI wiring, network layer.
- **`:wishlist-api`** — pure Kotlin/JVM module with **no code written by hand**: it contains only `src/main/resources/wishlist.yaml` (OpenAPI 3 spec). The `openapi` Gradle plugin generates Kotlin model classes (`ru.otus.wishlist.api.models.*`) from it at build time.

### Key directories (`app/src/main/`)
| Path | What it is |
|---|---|
| `java/ru/otus/wishlist/` | Root package: `application.kt` (App class + Hilt DI module), `MainActivity.kt`, `DtoMapper.kt`, `NetworkCallProcessor.kt`, `WizardCache.kt` |
| `java/.../fragment/` | Screens, grouped by feature: `login/`, `register/`, `main/`, `tab/` (bottom-nav tabs), `wishlists/`, `gifts/`, `users/` (+ `edit/` sub-screens). Each feature = Fragment + ViewModel + UseCase |
| `java/.../recyclerview/` | List-row adapters for wishlists / gifts / users |
| `java/.../service/` | Retrofit API interfaces (`AuthService`, `UsersService`, …) + OkHttp interceptors (`AuthInterceptor`, `SessionIdInterceptor`) |
| `java/.../storage/` | Serializable prefs objects (`UserPreferences`, `SessionPreferences`) + SharedPreferences (de)serialization extensions |
| `res/layout/` | Screen layouts (1:1 with fragments) |
| `res/navigation/` | Jetpack Navigation graphs — **this is the app's screen map** (`login_register.xml`, `main_navigation.xml`, tab graphs) |
| `res/values/`, `res/menu/` | Themes, strings, bottom-nav menu |
| `wishlist-api/src/main/resources/wishlist.yaml` | The API contract (generated code lives in `wishlist-api/build/`, don't read it) |

Ignore: `build/`, `.gradle/`, `.idea/`, `.kotlin/` (generated/build system).

### Entrypoints (execution flow)
1. **`settings.gradle.kts`** — declares the two modules.
2. **`app/src/main/AndroidManifest.xml`** — registers `WishlistApp` (the `Application`) and `MainActivity` (the launcher activity; the real "main function" of an Android app).
3. **`application.kt`** — `WishlistApp` (`@HiltAndroidApp`) + the single Hilt `Module`: provides `OkHttpClient`, JSON converter, and the four Retrofit service instances. **All DI wiring lives here.**
4. **`MainActivity.kt`** — single-activity host: installs the navigation graph, generates/stores a session id, checks login state (jumps to main screen or login), listens for logout, handles back button.
5. **`res/navigation/login_register.xml`** → `LoginFragment` → `AppMainFragment` → tab navigation graphs.

### Architecture pattern
Classic **MVVM** with a thin use-case layer, unidirectional data flow:

```
Fragment (UI, ViewBinding)
   ↓ observes LiveData, calls
ViewModel (@HiltViewModel, coroutines via viewModelScope)
   ↓ calls
UseCase (@ViewModelScoped) — thin wrapper per operation
   ↓ calls
Service (Retrofit interface)  → backend
```
Cross-cutting pieces:
- **`DtoMapper`** — maps generated API models → UI row models (`WishlistsItem`, `GiftsItem`, `UsersItem`).
- **`NetworkCallProcessor`** — wraps every HTTP call into `Result<T>`; on 401 it clears the cache and force-logs-out.
- **`WizardCache`** — in-memory, activity-scoped bag of "current user / current wishlist / current gift" shared across screens during a navigation flow.
- **Hilt** (DI, generated by KSP) — inject everything; **kotlinx.serialization** for JSON/prefs.

### Suggested order of reading
1. **`wishlist-api/…/wishlist.yaml`** — understand the domain and API contract first.
2. **`settings.gradle.kts` → `app/build.gradle.kts`** — modules and dependencies (Hilt, Retrofit, Navigation, coroutines).
3. **`AndroidManifest.xml` → `application.kt`** — how the app starts and everything gets injected.
4. **`MainActivity.kt` + `res/navigation/*.xml`** — the screen map and the login/logout flow.
5. **`storage/` + `service/`** (`AuthInterceptor`) — how auth state is stored and attached to requests.
6. **`NetworkCallProcessor.kt` + `WizardCache.kt` + `DtoMapper.kt`** — the three root-package helpers.
7. **One feature end-to-end** as a template — e.g. `wishlists/`: `WishlistsFragment` → `WishlistsFragmentViewModel` → `WishlistsFragmentUseCase` → `WishlistsService`.
8. **Remaining features** (`login/`, `register/`, `gifts/`, `users/`, `tab/`) — all follow the same Fragment/ViewModel/UseCase triplet.
9. **`res/layout/`** — only when you need to see how a specific screen looks.

That's it — small codebase (~60 Kotlin files), one clear pattern repeated per feature, and the only "generated" thing is the API model layer in `:wishlist-api`.

## Найденные проблемы

### Баги и потенциальные ошибки

**1. Scrolling the gift list silently fires "reserve" API calls for gifts the user never touched**
- File: `app/src/main/java/ru/otus/wishlist/recyclerview/gifts/GiftsItemViewHolder.kt`
- Lines: 37–50
- ```kotlin
  fun bind(item: GiftsItem) {
      ...
      reservedSwitch.isChecked = item.reserved      // line 42 — OLD listener still attached
      ...
      reservedSwitch.setOnCheckedChangeListener { _, _ ->
          onCheckedChange(item, absoluteAdapterPosition)   // line 47–49
      }
  }
  ```
- Problem: this `bind` runs every time a list row is reused (recycled) for a different item. At line 42 the switch is set programmatically *before* the new listener is installed, so the listener from the **previous** item is still active and fires with the old item when the checked state differs.
- Consequence: a stray `PUT /api/gifts/{oldGift}/reserve` reaches the server while the user is just scrolling (any mixed reserved/unreserved list triggers it). The server state flips against the user's intent, and the user's own just-made toggle can be cancelled. Silent data corruption, no error shown.

**2. Any 401 while on the login screen crashes the app**
- Files: `app/src/main/java/ru/otus/wishlist/NetworkCallProcessor.kt`, `app/src/main/java/ru/otus/wishlist/MainActivity.kt`
- Lines: NetworkCallProcessor 24–28; MainActivity 32–41
- ```kotlin
  response.code() == 401 -> {
      cache.clear()
      sharedPreferences.forceLogout()   // writes a blank token
      throw SecurityException()
  }
  // MainActivity: on that write it does
  navController.navigate(R.id.logout)
  ```
- Problem: the logout navigation action is defined only on the main-screen destination, not on the auth screens. But `forceLogout()` fires for *any* 401 — including a failed login attempt (bad credentials) or a late 401 from an in-flight request right after a manual logout.
- Consequence: `navigate(R.id.logout)` from the login screen can't resolve the action and throws an uncaught `IllegalArgumentException` → hard crash exactly when the user typed a wrong password, or right after logging out.

**3. Manual logout doesn't reset the "current user" → the next account inherits the previous one's view**
- Files: `app/src/main/java/ru/otus/wishlist/fragment/tab/profile/ProfileTabFragmentViewModel.kt`, `app/src/main/java/ru/otus/wishlist/fragment/wishlists/WishlistsFragmentViewModel.kt`
- Lines: ProfileTab 27–31; WishlistsFragmentViewModel 52–54
- ```kotlin
  fun logout() {
      sharedPreferences.logout()
      cache.wishlists.clear()
      cache.users.clear()      // currentUser / currentWishlist are NOT reset
  }
  ...
  val result = cache.currentUser?.id?.let { useCase.getUserWishlists(it) }
      ?: useCase.getAllWishlists()
  ```
- Problem: the shared in-memory cache survives logout (the activity isn't recreated). "Mine vs. someone else's" mode is decided solely by `cache.currentUser`, which manual logout leaves set (the 401 path resets it — this path doesn't).
- Consequence: user A browses user B's lists, logs out; user C logs in (same app process). C's "Mine" tab is titled "Wishlists of B", fetches B's wishlists, and hides the "add" button — cross-account data leak plus broken UI.

**4. Gift price is truncated to Int → fractional prices are silently rewritten on the server**
- Files: `app/src/main/java/ru/otus/wishlist/DtoMapper.kt`, `app/src/main/java/ru/otus/wishlist/fragment/gifts/edit/GiftsEditFragmentViewModel.kt`
- Lines: DtoMapper 31; GiftsEdit 49
- ```kotlin
  price = source.price?.toInt() ?: 0        // 19.99 → 19
  ...
  useCase.updateGift(id = id, name = name, description = description, price = price) // Int sent back
  ```
- Problem: the API price is a decimal number; the UI model narrows it to an integer, and the edit dialog sends that truncated value back.
- Consequence: a gift priced 19.99 displays as 19, and after any edit (name/description) the server price is permanently changed to 19 — silent data corruption.

**5. List diffing is broken by design → full rebinds and re-fired row states**
- Files: `app/src/main/java/ru/otus/wishlist/recyclerview/wishlists/WishlistsItemCallback.kt` (same in `gifts/GiftsItemCallback.kt`), `recyclerview/wishlists/WishlistsItem.kt`
- Lines: callback 7–15; item 12–13
- ```kotlin
  override fun areItemsTheSame(oldItem, newItem) = oldItem == newItem  // whole data-class equality
  override fun areContentsTheSame(oldItem, newItem) = oldItem.id == newItem.id
  ```
- Problem: the row models are mutable data classes with an embedded observable state (`MutableLiveData`) as a field, so "same item" means "the exact same instance" — a second equality check is never reached. Every list re-emit therefore looks like "all rows removed, all rows inserted".
- Consequence: full flicker/rebind and lost scroll position on every refresh or filter change; worse, rows keep their last in-row state in the LiveData, so a previously shown "error" alert or success toast re-pops on the next rebind.

**6. The SharedPreferences logout listener is never unregistered → activity leak**
- File: `app/src/main/java/ru/otus/wishlist/MainActivity.kt`
- Lines: 81 (no counterpart in `onDestroy`)
- ```kotlin
  sharedPreferences.registerOnSharedPreferenceChangeListener(logoutListener)
  ```
- Problem: the listener (a process-lifetime key-value store) holds a reference to the activity, and nothing removes it when the activity is destroyed.
- Consequence: every closed activity instance (view tree, navigation state) stays in memory until the process is killed — a steady leak over time.

**7. `WizardCache.clear()` forgets `filteredUsers`**
- File: `app/src/main/java/ru/otus/wishlist/WizardCache.kt`
- Lines: 22–31
- ```kotlin
  fun clear() {
      users = mutableListOf()
      currentUser = null
      // ... all fields reset EXCEPT filteredUsers
  }
  ```
- Problem: the "wipe flow state" routine (called on 401 and on every tab switch) skips one field that belongs to the same flow.
- Consequence: mostly latent — the next fetch overwrites it — but any code path that reads `filteredUsers` without refetching (e.g., if the refetch fails or is skipped) would show a stale user list from the previous session. Inconsistent reset is a bug waiting for a refactor to exploit it.

**8. Username filter is exact, case-sensitive match — not a search**
- File: `app/src/main/java/ru/otus/wishlist/fragment/users/UsersFragmentViewModel.kt`
- Lines: 49–54
- ```kotlin
  cache.usernameFilter.takeIf { it.isNotEmpty() }
      ?.let { it == user.username } ?: true
  ```
- Problem: the "filter" UI behaves like an exact full-string equality check.
- Consequence: typing "ivan" finds nothing for "Ivan" or "ivan_k"; users see an empty list and assume the data is missing. (Also note the fake "pagination" there: the backend already returned the full list, the app just re-slices it in chunks of 10 on scroll.)

**9. Only HTTP 200 counts as success**
- File: `app/src/main/java/ru/otus/wishlist/NetworkCallProcessor.kt`
- Lines: 22–30
- ```kotlin
  response.code() == 200 -> response.body() ?: throw IOException()
  else -> throw IOException()
  ```
- Problem: the app's single HTTP gate treats every non-200 (201 Created, 204 No Content, 400 with a useful body…) as a generic failure; the OpenAPI spec declares 200, so this only breaks if the real server deviates from it.
- Consequence: if the backend ever answers 201/204 for the create endpoints, the write succeeds on the server but the app shows a generic error and never adds the new item to its cache — UI permanently out of sync with the server, with no way to see the real error message.

### Архитектурные и структурные проблемы

#### 1. One global mutable object is the state bus of the whole flow
- **Problem.** The multi-step flow (user → wishlist → gift) is coordinated through `WizardCache` — a mutable singleton injected into everything (`@ActivityRetainedScoped` ≈ "lives as long as the app screen"). Screens read/write its `var` fields (current user, wishlist, gift, positions) instead of passing data to each other. Reset logic is duplicated and inconsistent, and it already produced a latent bug: `clear()` forgets one field.
- **Examples.**
    - `WizardCache.clear()` (`app/.../WizardCache.kt`) resets 8 of 9 fields — `filteredUsers` stays stale.
    - `ProfileTabFragment` logout does its own partial reset: `cache.wishlists.clear(); cache.users.clear()` — not `clear()`.
- **Solution.** Keep flow state in one explicitly-scoped state object with a single reset path, or pass the selected user/wishlist as navigation arguments between screens.

#### 2. Same screens reused with a hidden mode
- **Problem.** `WishlistsFragment` and `GiftsFragment` are mounted in *two* different tab graphs and behave completely differently ("own data" vs "someone else's"), but the mode is not a parameter of the screen — it's inferred from the global cache (`cache.currentUser == null`). A screen's behavior depends on hidden shared state, so it can't be reasoned about or tested from its own inputs.
- **Examples.**
    - `WishlistsFragment`: `currentUser == null` → "My" title + add button; non-null → "user's wishlists", add button hidden.
    - `GiftsFragment` row: `actionGroup.isVisible = getCurrentUser() == null` (edit/delete) vs. a "reserve" switch for others.
- **Solution.** Make the mode an explicit screen parameter (navigation arg like `ownerUserId: String?`, or a sealed `Mode`), so each screen's behavior is determined by its own inputs.

#### 3. Mutable row models with embedded live state break list diffing
- **Problem.** List rows are `data class`es with `var` fields *and* a reactive observable embedded as a field ("smart rows"). Kotlin data-class equality includes every field, so DiffUtil's identity check `oldItem == newItem` degenerates to reference equality — the built-in list diffing is effectively a no-op and every update must be poked manually (`notifyItemChanged(position)` / re-emit).
- **Examples.**
    - `data class WishlistsItem(..., var title: String = "", private val mDeleteState: MutableLiveData<DeleteState> = ...)` (`recyclerview/wishlists/WishlistsItem.kt`; `GiftsItem` similar).
    - `override fun areItemsTheSame(old, new) = old == new` — all three item diff callbacks.
- **Solution.** Immutable row models with state as plain values; diff by `id`; hold per-row operation state in the ViewModel keyed by item id.

#### 4. Logout is a side effect of a disk write (storage as event bus)
- **Problem.** "Logout" = writing a blank-token preferences object into SharedPreferences (the on-disk key-value store). `MainActivity` registers a SharedPreferences *change listener* and navigates to login whenever that key changes — so the persistence layer doubles as a global one-way event channel. The event type (voluntary vs. forced) is also stored inside the same preferences object. Any future code touching that key (token refresh, migration) will trigger app-wide navigation.
- **Example.**
    - `MainActivity`: `OnSharedPreferenceChangeListener { sp, key -> if (key == UserPreferences::class.simpleName) → navigate(R.id.logout) }`.
- **Solution.** An explicit auth-event stream (e.g. `StateFlow<AuthEvent>` from a session repository) observed by the UI; keep storage pure persistence.

#### 5. All failures collapse into one generic "Error"
- **Problem.** The single HTTP gateway maps every non-200 response to a plain `IOException` (401 → force-logout side effect + `SecurityException`), and every ViewModel does `catch (Throwable) → Error`. The UI can't distinguish "no network" from "server 500" from "validation failed", and error handling is split across two layers (processor throws, ViewModel catches) instead of being modeled as data.
- **Example.**
    - `NetworkCallProcessor.call`: `401 → cache.clear() + forceLogout() + throw SecurityException()`; anything else → `IOException`.
- **Solution.** A typed failure model (sealed class: `NetworkError` / `AuthExpired` / `Server(status, message)`) that ViewModels map to user-facing states.

#### 6. Project layout: monolithic `:app` + a half-used codegen module
- **Problem.** All features (auth, users, wishlists, gifts, cross-cutting) live in the single `:app` module. Meanwhile `:wishlist-api` runs OpenAPI codegen producing a *full* Retrofit client (`.api` + `.invoker` packages), but the app only consumes the generated **models** — the services are hand-written on top of separate Retrofit clients. Two sources of truth for the API surface, and the app can't be split into feature modules without first untangling this.
- **Examples.**
    - `wishlist-api/build.gradle.kts`: `compileKotlin dependsOn openApiGenerate` (full client generated each build).
    - App imports are only `ru.otus.wishlist.api.models.*` (e.g. `Login`, `LoginDto`) — the generated `.api`/`.invoker` code is dead weight.
- **Solution.** Pick one side for the API surface (use generated clients, or generate models only / hand-write DTOs); split features into Gradle modules if the app keeps growing.

---

**Minor smells (one line each):** fake client-side "pagination" — the backend returns full lists, the UI slices them 10-at-a-time on scroll; `UserPreferences` uses `var` fields and class-name-as-key; one separate Retrofit/OkHttp client per service instead of a shared one.

### Проблемы читаемости кода

#### 1. Legacy `m`-prefixed member fields
- **Problem.** Fields use the old Java "member" prefix (`mX`) combined with a manual public getter — a convention modern Kotlin dropped.
- **Example.** `WishlistsFragmentViewModel.kt`: `private val mDataState = MutableLiveData<DataState>(DataState.NotSet)` + `val dataState get() = mDataState`; same pattern as `mOperationState`, `mLoginState`, `mRegisterState` in other ViewModels.
- **Fix.** Drop the prefix (Kotlin convention: `_dataState` or a single `val` with private setter).

#### 2. Plural names for single row models
- **Problem.** One row/item is named with a plural, so a "single wishlist" reads as `WishlistsItem`, which clashes with the actual list type `List<WishlistsItem>`.
- **Example.** `recyclerview/wishlists/WishlistsItem.kt` (`data class WishlistsItem`), and `DtoMapper.kt`: `fun mapToWishlistsItem(source: Wishlist): WishlistsItem`. Same for `GiftsItem`, `UsersItem`.
- **Fix.** Singularize: `WishlistItem`, `GiftItem`, `UserItem`, `mapToWishlistItem`.

#### 3. `?: let { }` used as an "else" branch
- **Problem.** The elvis operator is chained onto `let { }` purely to get an else-branch — hard to parse, and it hides a plain conditional.
- **Example.** `WishlistsFragmentViewModel.kt` (`fillWishlistsFromCache`):
  ```kotlin
  cache.wishlists.takeIf { it.isEmpty() }?.let { loadWishlistsAndSaveToCache() }
      ?: let { mDataState.value = DataState.Loading; ... }
  ```
  Repeated in `GiftsFragmentViewModel.fillGiftsFromCache` and `WishlistsEditFragmentViewModel.createOrUpdateWishlist`.
- **Fix.** Replace with an explicit `if/else`.

#### 4. Names that don't match behavior
- **Problem.** Several method/class names describe only part of what the code actually does.
- **Example.** `WishlistsFragmentViewModel.fillWishlistsFromCache()` — also triggers a network fetch when the cache is empty (`loadWishlistsAndSaveToCache()`). `WishlistsEditFragmentViewModel.getToastText()` returns a string *resource id* (`R.string.wishlists_updated`), not text. `WishlistsEditFragment` doubles as the *create* screen (opened from `addButton` in `WishlistsFragment.kt`).
- **Fix.** Rename to reflect the full contract: `loadOrShowWishlists`, `getToastResId`, and either a shared `WishlistsEditCreateFragment` or a `mode` parameter documented in the name.

#### 5. Copy-pasted state types and visibility boilerplate
- **Problem.** The identical 5-state sealed class (`NotSet/Loading/Content/Empty/Error`) is redefined per ViewModel, and every fragment re-implements a ~35-line `when` that toggles four `isVisible` flags per branch.
- **Example.** `DataState` duplicated in `WishlistsFragmentViewModel`, `UsersFragmentViewModel`, `GiftsFragmentViewModel`; the `when` block in `WishlistsFragment.kt` (lines 113–146) is nearly verbatim in the other two list fragments.
- **Fix.** One shared `ScreenState` type plus a single `fun bindState(state)` helper (or extension) per screen.

#### 6. ViewModels that reach into the view layer
- **Problem.** ViewModels take generated view-binding classes as parameters and hand back UI listeners, which blurs the layer boundary and duplicates a ~30-line scroll listener three times.
- **Example.** `UsersFragmentViewModel.fillUsersFromCache(binding: FragmentUsersBinding)` (sets `binding.clearFilterButton.isVisible`); `WishlistsFragmentViewModel.getOnScrollListener(adapter, pageSize)` returns an anonymous `RecyclerView.OnScrollListener` — nearly identical copies exist in `UsersFragmentViewModel` and `GiftsFragmentViewModel`.
- **Fix.** ViewModel exposes plain state; the fragment creates the scroll listener (a small shared `RecyclerView` helper) and binds views itself.

#### 7. Row adapters leak layout internals via an `onBind` callback
- **Problem.** The adapter's constructor takes an `onBind` lambda whose parameter list is raw view widgets; the parameter list grows as the row layout grows, and the fragment ends up manipulating row view groups.
- **Example.** `GiftsItemAdapter(onCheckedChange, onEditButtonClicked, onDeleteButtonClicked, onBind: (GiftsItem, Group, Group, Group, SwitchCompat) -> Unit)`; `WishlistsItemAdapter` has the 3-variant.
- **Fix.** Move row-state wiring into the ViewHolder/adapter; fragments pass only business actions (item, position).

#### 8. Generic and cryptic names for shared symbols
- **Problem.** Top-level constants `RESULT`/`SUCCESS` are too generic to be self-explanatory outside their file, and the shared cross-screen state holder has an opaque name.
- **Example.** `fragment/constants.kt`: `const val RESULT = "result"`, `const val SUCCESS = "success"` (imported by ~6 fragments); `WizardCache` — nothing in the name says it holds the users→wishlists→gifts navigation state.
- **Fix.** Namespace them (e.g. `FragmentResult.SUCCESS`) or make them an `enum`; rename the cache to something descriptive like `FlowCache`/`NavigationFlowState`.

## Рекомендации по улучшению

### Priority 1 — data integrity and crashes (fix first)
1. **Stop stale row listeners from firing network calls** (bug 1): attach a single listener that reads the *current* item, or replace the listener before setting the control's state — never leave the previous bind's listener active.
2. **Make 401 handling crash-safe** (bug 2): on the login screen a 401 should show a validation error, not navigate; centralize logout in one place and only trigger it when resolvable.
3. **Reset all cross-session state on logout** (bugs 3, 7): one `clear()` path that resets every flow field; remove the ad-hoc partial resets.
4. **Keep prices as decimals end-to-end** (bug 4): don't narrow the API type to `int` before sending it back.
5. **Treat all 2xx as success** (bug 9): the single HTTP gate should not fail on 201/204 if the server ever returns them.

### Priority 2 — architecture (removes the source of future bugs)
6. **Replace the global mutable cache** (`WizardCache`) with explicit data flow: pass data as navigation arguments between screens, or keep one scoped state object with a single reset path.
7. **Make screen modes explicit parameters** ("own data" vs "someone else's") instead of inferring them from shared state.
8. **Model errors as data**: a typed failure type (network / auth expired / server error with status) mapped in the ViewModel, instead of one generic `IOException` + `catch (Throwable)`.
9. **Decouple events from storage**: unregister the preferences listener on teardown; drive navigation from an explicit auth-event stream, not from a disk write.
10. **One source of truth for the API surface**: use the OpenAPI-generated client, or generate models only — don't keep both a dead generated client and hand-written services.

### Priority 3 — quality, tests, readability
11. **Add a small test suite where the bugs were found**: the 401/logout flow, list-row rebind (the scroll-reserve bug), and price mapping.
12. **Deduplicate**: one shared screen-state type + one `bindState` helper; immutable row models with per-row state kept in the ViewModel keyed by id; one shared list-diffing/scroll helper.
13. **Cleanup pass**: drop `m`-prefixed fields, rename misleading symbols (`WishlistsItem` → `WishlistItem`, `fillWishlistsFromCache`, `getToastText`, `WizardCache`), replace `?: let { }` with `if/else`, namespace `RESULT`/`SUCCESS`.

## Итоговый вывод

- **Structure is fine, state handling is not.** MVVM layering, DI, and the API-client stack are textbook and easy to navigate. All the problems come from ad-hoc cross-cutting design: a global mutable cache acting as the app's state bus, the on-disk key-value store doubling as an event channel, and all failures collapsed into one generic error.
- **The bugs are the consequence, not the cause.** Silent server-side data changes on scroll, the crash on a wrong password, and one account's data leaking into the next are direct results of the items above — fixing the architecture removes the whole class of such bugs.
- **No safety net.** Zero tests and zero documentation mean nothing in the current process can catch these issues; the code compiles and "works" until a real user hits a bad path.
- **Verdict:** a solid educational skeleton with modern, well-chosen tooling, but not production-ready. The five Priority-1 fixes plus a small test suite covering the logout flow and list rows would remove most of the risk.
